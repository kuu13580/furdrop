# 要件定義書 - FurDrop

## 1. サービス概要

不特定多数の撮影者（送信者）から、写真を受け取るためのサービス。
受信者が公開URLを発行し、送信者がそのURLに匿名で写真をアップロードする。

**ユースケース例:**
- イベント・ライブの参加者に「撮った写真をここに送ってください」と案内
- 名刺やSNSプロフィールにURLを掲載し、継続的に写真を受け付ける

### 1.1 他サービスとの差別化

既存の写真共有・ストレージサービス（Google Drive, Dropbox, AirDrop等）との差別化ポイント:

| ポイント | 説明 | 既存サービスの課題 |
|---|---|---|
| **匿名送信に特化** | 送信者・受信者ともにメールアドレス等のプライベート情報を交換せずに写真を送受信できる。URLを知っていれば誰でも送信可能 | Google Drive等は送信者にアカウント登録が必要。AirDropは物理的近接が必要 |
| **送信者情報を写真ファイルに残せる** | 送信者は透かしで画像に焼き込み (受信者が R14 で可否を制御)、受信者は DL 時に EXIF へ送信者名を記録できる (R17)。不可逆な加工は送信者が選び、可逆なメタデータは受信者が選ぶ。匿名性と追跡可能性を両立しつつ、双方の意図しない加工を防止 | 匿名送信では「誰が送った写真か」の管理が困難。他サービスは送信者/受信者どちらの立場も考慮した制御がない |
| **写真受信に特化したUX** | 送信者名・日付でのソート/グルーピング、一括DL、ストレージ管理など、「大量の写真を受け取って管理する」ワークフローに最適化 | 汎用ストレージは写真受信に特化した管理機能がない |
| **DL期限による自動削除** | 受信した写真に閲覧期限を設け、期限後に自動削除する。無料のストレージサービスとして悪用されることを防止 | 無制限保存が前提のサービスが多く、コスト管理が困難 |
| **受信通知** | 写真を受信したらプッシュ通知で即座に知らせる。イベント中のリアルタイム受信に対応（**Phase 2**: MVP では未実装） | メール共有は通知が埋もれやすい |
| **セキュリティ（画像専用）** | サーバーサイドで画像フォーマットを検証し、画像以外のファイルをブロック。悪意あるファイルの送信を防止 | 汎用ファイル共有は任意のファイルをアップロード可能 |

## 2. ユーザー種別

| 種別 | 説明 | 認証 |
|---|---|---|
| 受信者 | 写真を受け取る人。アカウント登録が必要 | Firebase Auth（Twitter OAuth等） |
| 送信者 | 写真を送る人。匿名でURLにアクセス | 不要 |

## 3. 機能要件

### 3.1 受信者機能（認証必須）

| ID | 機能 | 優先度 | 説明 |
|---|---|---|---|
| R01 | アカウント登録 | MUST | Twitter OAuth等でログインし、公開URL用スラッグを設定 |
| R02 | 公開URLの発行・共有 | MUST | `https://domain/send/:handle?k=KEY` 形式（アクセスキー付き）。QRコード表示・コピー機能。詳細は R16 |
| R03 | 受信写真の一覧表示 | MUST | サムネイルグリッド。ページネーション（無限スクロール） |
| R03a | ソート・グルーピング | WANT | 日付別・送信者別でのソート切替、セクション見出しによるグルーピング表示。写真選択・DL時の視認性向上。日付の境界は受信者のブラウザのタイムゾーンに従う (`tz_offset_min`) |
| R04 | 写真の詳細表示 | MUST | メタデータ（送信者名、ファイル情報）表示 |
| R05 | オリジナル画像のDL | MUST | 単体DL。署名付きURLで直接DL |
| R06 | 写真の削除 | MUST | 単体・一括削除。ストレージ使用量を即時反映 |
| R07 | ストレージ使用状況表示 | MUST | 使用量/上限をプログレスバーで表示 |
| R08 | 一括ダウンロード | WANT | 複数選択→Workers がストリーミング ZIP を1本のレスポンスで返す。1回の上限は合計 3.5GB。詳細は下記 |
| R09 | プッシュ通知（新着写真） | Phase 2 | FCM経由。設定画面でON/OFF。MVP では未実装。MVP リリース後に追加導入予定 |
| R10 | プロフィール編集 | WANT | 表示名・スラッグ変更 |
| R11 | 受付停止/再開 | MUST | 一時的にアップロードを停止する機能。設定画面 (S10) の「写真を受け付ける」チェックボックスで `users.is_active` を切り替える。停止中は `GET /send/:handle` が `is_accepting=false` を返し、`POST /send/:handle/sessions` は 403 FORBIDDEN。R16 の opt-out を選んだ受信者にとっては、意図しない送信を止める唯一の安全弁になる |
| R12 | フィードバック・不具合報告 | MUST | フッターにGoogleフォームへのリンク（メール収集OFF） |
| R13 | DL期限・自動削除 | MUST | 受信した写真に閲覧期限を設ける（デフォルト365日）。受信時に `photos.expires_at` へ実値を焼き込み、期限後は自動削除される。無料ストレージとしての悪用防止。詳細は下記 |
| R14 | 受信オプション設定 | MUST | 送信者に提示するオプションを受信者が制御できる。設定画面で切替 |
| R15 | アカウント削除 | MUST | 受信者が自身のアカウントと関連データ（写真・R2 オブジェクト）を完全に削除できる。設定画面から、自身のハンドルを再入力する確認ステップを経て実行。送信者の通信記録は規約第13条の最低3か月保存期間に従い保護 |
| R16 | 送信URLアクセスキー | MUST | 受信URLには `?k=KEY` 形式のアクセスキーを付与する。キーが合致しない送信は拒否される（handle のみ知っている第三者が送信できないようにするため）。1 受信者に対し N キーを保持できるスキーマで実装し、将来の有効期限・再生成・無効化等の機能拡張に備える。MVP では「永続的に有効なキーを 1 つ自動発行」のみを提供する。受信者は警告のうえでキー検証を無効化 (opt-out) できる |
| R17 | DL時のEXIF埋め込み | WANT | 受信者がダウンロードする写真の EXIF に送信者名を記録できる。記録先は「記録しない / 撮影者(Artist)欄のみ / カメラ機種(Model)欄にも記録」の3択。埋め込みは DL するファイルに対してのみ行い、R2 の保存物は変更しない |

**R08 一括ダウンロードの詳細:**

複数選択した写真を **Workers がストリーミング ZIP に固めて 1 本のレスポンスで返す**。

- **なぜサーバーで作るのか**: クライアントで ZIP を組み立てると Blob にメモリ上で全量が
  溜まる。**iOS の WebKit は Blob をディスクへ退避できない**ため、15MB/枚なら推定 40〜70 枚で
  タブが無言で死ぬ (例外もエラー表示もなく、モーダルごと消える)。サーバーから
  `Content-Disposition: attachment` で流せば、ブラウザのダウンロードマネージャが単体DLと
  同じようにディスクへ逐次書きするので枚数に依存しなくなる
- **1 回の上限は合計 3.5GB** (一眼 JPEG 15MB/枚で約 230 枚、スマホ 3MB/枚で約 1,150 枚)。
  超過分は 400 で拒否して分割を促す。Workers の CPU 上限が実質の制約で、
  実測 27 CPU-ms/MiB に対し `[limits] cpu_ms = 120000` を設定している
- **進捗表示は持たない**。ブラウザのダウンロードマネージャが出すので、アプリ側の進捗
  モーダルは廃止した。`Content-Length` も付けない (chunked)
- **1 バイトも書く前に分かる失敗 (R2 に対象が無い) はスキップして `MISSING.txt` を同梱**し、
  ZIP を正常に閉じる。途中で切れた ZIP はブラウザが「DL 完了」として保存してしまうため。
  エントリ本体の転送中に落ちた場合だけは abort しかなく、壊れた ZIP が残る
- 発火は隠しフォームの POST (`target="_self"`)。ブラウザの DL は `Authorization` ヘッダを
  送れず、API は別オリジンなので Cookie も使えないため、トークンをボディに載せる

**R13 DL期限の詳細:**

- **期間**: 受信から 365日。`workers/src/lib/retention.ts` の `PHOTO_RETENTION_SECONDS` が唯一の定義
- **焼き込み方式**: 期限は Presigned URL 発行時 (`POST /send/:handle/sessions/:sessionId/photos`) に `photos.expires_at` へ実値として書き込む。Cron の `COALESCE(expires_at, created_at + 365日)` は、`0009_extend_photo_retention.sql` のバックフィルより前に入った旧データと、「migration 適用 → 新コードのデプロイ」の隙間に届いた行のためのフォールバック
- **なぜ定数で判定しないか**: 定数だけで判定すると、将来この値を短くしたときに「短縮後の期限を既に過ぎている写真」が次回 Cron で一斉に物理削除される。実値を焼き込んでおけば、定数変更は新しく届く写真にだけ効く。遡及させたい場合は 0009 のように migration で明示的に行い、履歴に残す
- **受信者への予告 (R13 UI)**: `GET /receiver/quota` の `expiring_soon` (60日以内に期限を迎える件数と最も早い期限) をダッシュボードのバナーに使う。ギャラリーのサムネイルバッジは残り14日 / 3日でフロント側が判定する。プッシュ通知 (R09) は Phase 2 のため、予告のチャネルは「ログイン時に画面で気づく」のみ。バナーの窓を広く取っているのはそのため
- **受信者による期限の延長・解除**: 現状は手段を持たない。焼き込み方式なので、将来的にはスキーマ変更なしに個別延長を載せられる。利用規約第12条2項が「原則として365日」としているのはそのため

**R15 アカウント削除の詳細:**

- 削除対象: `users` レコード、関連する全 `photos` レコードと R2 のオリジナル画像/サムネイル全件
- **送信者の通信記録は保護**: 利用規約第13条 / プライバシーポリシーで「送信者の通信記録 (`sender_ip` / `sender_ua`) は当該送信から最低3か月保存」を保証しているため、`upload_sessions` のうち 100日 (Cron `pruneOldSessionLogs` の閾値) 経過済みのもののみ物理削除し、保存期間中のセッションは保持する。残された孤児セッション (receiver 削除済み) は Cron `cleanupOrphanedSessions` が 100日経過後に物理削除する
- 確認方法: 設定画面の専用ダイアログで自身のハンドルを再入力（誤操作防止）。サーバ側でも一致を検証
- Firebase Auth ユーザー: クライアントの `deleteUser()` で best-effort 削除。Workers では Firebase Admin SDK を利用できないため Firebase ユーザー削除はサーバから実行できない。`requires-recent-login` 等で失敗しても Workers のデータは既に削除済みのため、次回ログイン時に `GET /auth/me` が 404 を返し登録画面に遷移する自然なリカバリで吸収される
- R2 オブジェクト削除: レスポンスを早く返すため `ctx.waitUntil` で背景実行。失敗した場合は孤立オブジェクトが残るが、ユーザー削除は頻度が低く許容
- 復元: 不可。再登録は同一ハンドルが空いていれば可能

**R14 受信オプション設定の詳細:**

送信者情報の埋め込み方式は画像への影響度が異なるため、受信者が方式ごとに「無効 / 任意 / 必須」の3値を設定できる。

| モード | 意味 |
|---|---|
| `disabled` | 送信者の画面に表示しない。サーバ側でも該当フィールドは保存されない |
| `optional` | 送信者が任意で有効化できる |
| `required` | 送信者は必ず埋め込みを行う。サーバ側でも該当フィールド未指定時は400を返す |

| オプション | デフォルト | 画像への影響 | 受信者が制御する理由 |
|---|---|---|---|
| 送信者名入力 (S03) | 任意 | なし（DB保存のみ） | 「名前だけは必ず欲しい」受信者向けに **必須化** (`require_sender_name`) を選べる。埋め込み設定とは独立の2値 (任意/必須)。必須時は `POST /send/:handle/sessions` が `sender_name` 未指定を400で拒否する |
| 透かし (S05) | `disabled` | **不可逆**（画像を直接加工） | 受信者の意図しない透かしが入ると元に戻せない。`required` は強い帰責性を伴うため慎重に |

送信者のアップロード画面では `disabled` 以外のオプションのみ表示される。`required` の場合はチェックボックスが強制ONになり外せない。

送信者名が必須になる条件は「`require_sender_name` が有効」であることのみ。透かしの `required` は自由テキストで成立するため送信者名は要求せず、「透かしを必ず入れる (非空テキストの要素が1つ以上ある)」ことのみ強制する。内容までは縛らない (クライアントサイドで焼き込む以上、内容の強制は技術的に担保できない)。サーバは `watermark_text` の非空のみ検証する。

**R16 送信URLアクセスキーの詳細:**

- **目的**: handle (公開スラッグ) のみを知る第三者が、受信者の許可なく送信を開始できる状態を防ぐ。受信URL `https://domain/send/:handle?k=KEY` の `k` クエリパラメータがそのハンドルの有効なキーのいずれかと一致しない場合、`POST /send/:handle/sessions` は `403 INVALID_KEY` を返す
- **検証タイミング**: セッション作成 (`POST /send/:handle/sessions`) でのみ検証する。`GET /send/:handle` (受信者プロフィール表示) はキーを要求しない — プロフィール自体は公開情報として扱う
- **DB**: `send_keys (id, receiver_id, key_value UNIQUE, created_at, updated_at)`。1 受信者 : N キーの関係。「無効化」はレコード削除で表現（CRUD は最小限）。将来の `expires_at` / `name` / `is_active` 等は必要時に ALTER で追加する
- **生成方式**: 新規発行は Workers の `generateSendKey()`（`crypto.getRandomValues` + URL-safe 64 文字、デフォルト 21 文字＝126 bit エントロピー、nanoid 同等）。既存ユーザーの初期発行はマイグレーション SQL 内で SQLite ネイティブの `lower(hex(randomblob(16)))` を使用（32 文字 HEX、128 bit）
- **初期発行**: 新規受信者登録時 (`POST /auth/register`) にユーザー作成と同時にキーを 1 つ自動発行する。既存ユーザーには `0007_send_keys.sql` マイグレーションで 1 件ずつ初期発行
- **保存方式**: 平文。URL に乗せて配布する性質なので保護効果は限定的で、UI で「現在のキーをそのまま表示してコピー」できる UX を優先
- **MVP の UI**: ダッシュボードの公開URLカードに `?k=KEY` 付きの完全 URL を表示するのみ。キー一覧管理画面・複数キー UI・再生成 UI は MVP では実装しない（DB スキーマだけ拡張可能性を保つ）。Workers の `GET /auth/me` / `PATCH /auth/options` は受信者の `send_keys` から最も古い 1 件を選んで `receive_url` に結合して返す
- **アカウント削除との関係**: `DELETE /auth/account` の batch に `DELETE FROM send_keys WHERE receiver_id = ?` を含めて同期削除する

**R16 opt-out (キーを使わない受信) の詳細:**

キーは「handle だけを知る第三者に送信させない」ための仕組みだが、URL が長くなる・途中で切って共有され 403 になる (issue #82 項目19) といった UX コストを伴う。名刺や SNS で `@handle` だけを見せて受け取りたい受信者のために、受信者自身の意思で無効化できるようにする。

- **設定**: `users.require_send_key` (0/1、既定 1)。設定画面 (S10) の「受信URLを知っている人だけから受け取る」チェックボックスで切り替える。オフにするときのみ確認ダイアログで「ハンドルを知っている人なら誰でも送れる状態になる」ことと「受付停止 (R11) でいつでも止められる」ことを提示する
- **サーバ挙動**: `require_send_key=0` の受信者に対しては `POST /send/:handle/sessions` がキーを検証しない。`?k=` が付いていても、古い / 誤ったキーでも受け付ける (配布済み URL を壊さないため)
- **send_keys は削除しない**: opt-out はフラグのみで表現する。再度オンにすれば以前と同じ受信URLが復活し、配布済みの `?k=` 付き URL がそのまま使える
- **receive_url**: opt-out 中は `GET /auth/me` / `PATCH /auth/options` が `?k=` を落とした素の `/send/:handle` を返す。ダッシュボードのコピー・QR・シェアは `receive_url` 由来なので自動で短い URL に切り替わる
- **プロフィール API**: `GET /send/:handle` が `require_send_key` を返す。送信者フロントは「`?k=` の無い URL が正当かどうか」をこれで判断し、キー必須の受信者に対してのみ写真の加工前にエラーを出す
- **濫用対策**: opt-out した受信者は handle さえ当たれば送信されうるため、handle 列挙の速度を落とす目的で `GET /send/:handle` にも送信者IP単位のレート制限を追加する (X05)。空振り (存在しない handle) のときだけカウントするので、正規の送信者は共有 IP でも影響を受けない。ただし本質的な守りは R11 の受付停止・写真の削除・通報運用であり、レート制限は補助的なもの
- **法務との関係**: 利用規約第2条5号は公開URLを `https://[ドメイン]/send/[ハンドル]` と定義し、第9条 / プライバシーポリシー第11項も送信者を「公開URL（ハンドル）を知る不特定の者」と規定している。キーの有無に関わらず規約上の位置づけは変わらない

**R17 DL時のEXIF埋め込みの詳細:**

EXIF はメタデータで可逆 (あとから除去できる) なので、透かしと違い「実際にファイルを手元に置く受信者」が DL 時に決める。送信者側の EXIF オプションは廃止した。

- **記録先**: `記録しない` / `撮影者 (Artist) 欄のみ` / `カメラ機種 (Model) 欄にも記録` の3択。Artist は Lightroom や Adobe Bridge で表示され元のカメラ情報を壊さない。Model は Google フォトや iOS の写真アプリでも表示されるが元のカメラ機種名を上書きする
- **記録する文字列**: `Photo by ` + 送信者名 (先頭の `@` は除去)。Artist / Model は仕様上 ASCII 専用の欄で非 ASCII は慣習頼みになるため、接頭辞はロケールに関わらず英語で固定する。送信者名が無い写真 (匿名送信) は無加工でスキップする
- **実行場所**: 単体 DL は受信者のブラウザ (presigned GET で取得したバイト列に `piexifjs` で APP1 セグメントを差し替えて保存)、**一括 DL は Workers** (R08 でバイトが Workers を通るため、そこで差し替える)。どちらも R2 に保存されているオリジナルは送信者が送ったまま変わらない。サーバー側は先頭 256KB だけバッファして APP1 を差し替え、残りはパススルーする (1 枚あたり約 1ms、写真サイズに依存しない)
- **設定**: localStorage (`furdrop.downloadOptions`)。端末ごとの好み (どのアプリで写真を見るか) に紐づくのでサーバには持たせない。**初回 DL のときに一度だけダイアログで選ばせ**、以降は保存値で即 DL する。設定画面 (S10) には置かない (受信オプションではないため)。ギャラリーの選択バーと写真詳細に「ダウンロードオプション ▾」を常時出し、そこから変更できる
- **単体 / 一括の両方**: 一括 DL (R08) は Workers が ZIP に入れる直前に書き込む (フォームの `exif_credit` で受信者の選択を渡す)。「記録しない」を選んでいる単体 DL は presigned URL への直リンクのままにして、無加工の最速パスを保つ
- **失敗時**: 記録に失敗しても DL 自体は成立させる (無加工のまま保存)。単体はインライン通知、一括は無加工のまま ZIP に含める。piexif が読めない EXIF (MakerNote が濃いファイル等) も無加工にする — 読み替えると Orientation や撮影日時が消えるため
- **既知の制限**: piexif は EXIF を load → dump で再直列化するため、MakerNote / MPF (iPhone の HDR ゲインマップ等) の内部に絶対オフセットを持つデータが壊れる可能性がある (**未検証**)。記録先を Artist のみにすれば影響は小さい
- **既存写真**: 送信者が EXIF 埋め込みを選べた頃の写真は Model 欄に送信者名が焼かれた状態で R2 にある。あとから消せないが、DL 時の処理は全写真で同じ (Artist を足す / Model も選べば上書き)

### 3.2 送信者機能（認証不要）

| ID | 機能 | 優先度 | 説明 |
|---|---|---|---|
| S01 | 受信者のランディングページ表示 | MUST | 受信者名・プロフィール表示。受付状態確認。URL の `?k=KEY` は後続ページに引き回されるが、ランディング表示自体は handle のみで可能 |
| S02 | 複数枚写真アップロード | MUST | ドラッグ&ドロップ + ファイルピッカー。JPEG/PNG/HEIC対応（クライアントでJPEGに変換） |
| S03 | 送信者名の入力 | MUST | 任意。TwitterID等を入力可能。DBに保存され受信者に表示 |
| S05 | 透かし（ウォーターマーク）埋込 | WANT | クライアントサイドでCanvas描画。テキストと四角形 (文字の下地) の要素を合計最大5個、プレビュー上のドラッグで自由配置。テキストはフォント (Google Fonts 日本語 24種)・サイズ・透明度・色 (明暗ペアのパレット=背景輝度で自動選択 / カスタム固定色)・縁取りを、四角形は幅・高さ・角丸・透明度・色を要素ごとに設定できる。四角形は常にテキストの背面に描画。テキストは送信者名連動 (編集で解除) または自由入力。デザインは localStorage に永続化されリピート送信で再利用される。画像に視覚的に送信者情報を残す手段 |
| S06 | アップロード進捗表示 | MUST | ファイルごとの進捗バー |
| S07 | 送信完了画面 | MUST | 完了メッセージ + 送信した写真のサムネイル一覧 |

### 3.3 システム機能

| ID | 機能 | 優先度 | 説明 |
|---|---|---|---|
| X01 | サムネイル生成 | MUST | クライアントサイド。長辺400px, JPEG品質0.7 |
| X02 | ストレージクォータ管理 | MUST | 受信者ごとの総容量制限。アップロード時に二重チェック |
| X03 | アップロードセッション管理 | MUST | 複数枚を1セッションにまとめる。1セッション最大100枚。1時間で期限切れ |

| 項目 | 目標 |
|---|---|

### 4.3 可用性・スケーラビリティ

| 項目 | 値 |
|---|---|
| 初期想定ユーザー数 | 最大100受信者 |
| 同時送信者数 | 特に制限なし（Workers自動スケール） |
| 可用性目標 | Cloudflareプラットフォーム依存（99.9%+） |

### 4.4 セキュリティ

| 項目 | 対策 |
|---|---|
| 認証 | Firebase Auth IDトークン + Workers側で署名検証 |
| 認可 | 受信者は自分の写真のみアクセス可能 |
| ストレージアクセス | R2は全てプライベート。署名付きURLのみでアクセス |
| 送信者の認可 | 受信URL の `?k=KEY` アクセスキー (R16) でセッション開始を制限、以降はセッションID（UUID v4）の知識に基づく。受信者が opt-out した場合は handle の知識のみが条件になる |
| 画像の公開範囲 | 受信者のみ（プライベート） |
| NSFW検出 | 不要（初期リリース） |
| 通報機能 | 将来検討 |

|---|---|

| 項目 | 値 |
