# 受信者向けメール通知の法務整理 — 規約・プライバシーポリシーに何を書くか

> **2026-08-31 時点の調査。** 対象は「受信者が任意で通知先メールアドレスを登録し (double opt-in)、新着写真ダイジェスト / 削除予告 / 容量警告の3種を Cloudflare Email Service で送る」機能。
> **筆者は弁護士ではない。** 本書は条文・ガイドライン・事業者の公式文書という一次情報に当たって整理したものであり、法的助言ではない。結論はいずれも「〜と考えられる」レベルであり、**公開前に弁護士のレビューを受けることを推奨する**。
> 各主張には条文番号と一次情報の URL を付けた。一次情報が取れなかった項目は **[一次情報なし]** と明記している。

## 結論: 何を追記すれば足りるか

1. **プライバシーポリシー第2項・第3項・第5項・第11項の4か所**を直せば足りる。第6項 (越境移転) と第10項 (外部送信規律) は**追記不要**と考えられる (理由は §論点2 / §論点5-3)。
2. **委託先テーブル (第5項) は Cloudflare 行の「委託内容」「情報の例」に追記する。行は増やさない** — 事業者・所在国・契約関係のいずれも変わらないため。
3. **利用規約は第3条 (アカウント登録) と第5条 (サービス内容) に各1項ずつ**。通知先アドレスの登録・検証・解除と、メールの到達を保証しないことを書けば足りる。
4. **通知メールは特定電子メールに該当しない**と整理できると考えられる。ただしそれは**メール本文に広告・宣伝 (とくに有料プランの案内) を一切入れないという設計上の約束**に依存する。入れた瞬間に、個人事業主の**本名と住所の表示義務** (法4条1号・施行規則9条2号) が発生し、現在の「氏名・住所非公表」方針と正面から衝突する。
5. **保存期間 (第11項) は4行追加**。検証トークン24時間 / 通知先アドレスと通知設定はアカウント有効中 / 送達ログ90日 (既存の「アクセスログ 原則90日」に揃える)。規約13条の「最低3か月」は**送信者の通信記録**の規律なので、通知メールのログには及ばない。改定は**効力発生前の事前告知** (privacy.md 第13項2項 / 規約第19条2項) と、設定画面での**利用目的の明示** (個情法21条2項) とセットで行うこと (§B-4)。

## 論点1: 特定電子メール法 — 該当しないと整理できるか

### 1-1. 条文上の当てはめ

**「特定電子メール」の定義 (法2条2号)** — [e-Gov 法令検索 / 特定電子メールの送信の適正化等に関する法律](https://laws.e-gov.go.jp/law/414AC0100000026)

> 二　特定電子メール　電子メールの送信（…）をする者（**営利を目的とする団体及び営業を営む場合における個人**に限る。以下「送信者」という。）が**自己又は他人の営業につき広告又は宣伝を行うための手段として**送信をする電子メールをいう。

要件は2つある。

| 要件 | FurDrop の当てはめ |
|---|---|
| 送信者が営利団体または営業を営む個人 | **満たすと考えるのが安全**。現状は無料サービスだが、requirements.md §6 が「有料プラン（Coming Soon）」を掲げている以上、「営業を営む場合における個人」に当たらないという主張に依拠すべきではない |
| 広告又は宣伝を行うための手段として送信 | **満たさないと整理できると考えられる**（下記） |

### 1-2. 「広告又は宣伝を行うための手段として」の解釈 — ガイドラインの列挙

[総務省総合通信基盤局消費者行政課・消費者庁取引対策課「特定電子メールの送信等に関するガイドライン」平成23年8月](https://www.soumu.go.jp/main_sosiki/joho_tsusin/d_syohi/pdf/m_mail_081114_1.pdf) 1①1) p.1〜2。**これが最新版である**ことは[消費者庁の掲載ページ](https://www.caa.go.jp/policies/policy/consumer_transaction/specifed_email)で確認した (平成23年8月31日改正が最後)。

該当する例:

> ア）営業上のサービス・商品等に関する情報を広告又は宣伝しようとするウェブサイトへ誘導することがその送信目的に含まれる電子メール
> イ）ＳＮＳ（Social Network Service）への招待や懸賞当選の通知、友達からのメールや会員制サイトでの他の会員からの連絡などを装って営業目的のウェブサイトへ誘導しようとする電子メール

該当しない例:

> ア）取引上の条件を案内する事務連絡や料金請求のお知らせなど**取引関係に係る通知であって広告又は宣伝の内容を含まず、広告又は宣伝のウェブサイトへの誘導もしない**電子メール
> イ）単なる時候の挨拶であって、広告や宣伝の内容を含まず広告又は宣伝のウェブサイトへの誘導もしない電子メール

3種の通知はいずれも、受信者が締結済みの利用契約 (規約第2条1項1号) の履行に関する事務連絡であり、上の「該当しない例ア）」の類型に最も近いと考えられる。

- **新着写真ダイジェスト** — 受信者宛に届いた写真の件数の通知。サービスの中核機能の実行結果の報告
- **削除予告** — 規約第12条2項の365日自動削除の予告。受信者の財産 (写真) が消える前の告知であり、通知しないことのほうが問題になりうる
- **容量警告** — 規約第12条1項の上限に対する使用状況の告知

**ただし、これは「例示」である。** ガイドラインは「次のような電子メールについては…特定電子メールには当たらない**ものもある**」という書き方をしており、類型的なセーフハーバーを与えているわけではない。**専門家の確認を推奨する。**

### 1-3. 実務上の分岐点 — 本文に何を書くかで結論が変わる

上記2つの列挙を並べると、**判定は「送信の目的の種類」ではなく「本文の内容」で決まる**構造になっている。該当しない例の両方に「広告又は宣伝の内容を含まず、広告又は宣伝のウェブサイトへの誘導もしない」という条件が明示的に付いているためである。

したがって**メールテンプレートの設計ルールとして次を守る必要があると考えられる**。

- **有料プランの案内・アップセルを本文に入れない。** とくに危険なのは**容量警告 (95%)** で、「上限を緩和するには有料プランへ」という導線を置きたくなる場面だが、これを入れると要件2を満たし、特定電子メールになると考えられる (requirements.md §6 は有料プランを「Coming Soon」としており、実装時に入り込むリスクが現実にある)
- 本文中のリンクは、**当該通知に対応するための遷移先** (ギャラリー、設定画面、配信停止) に限る。LP・料金ページ・新機能紹介ページへのリンクを置かない
- フッターのサービス名・ロゴ・サービス URL そのものは、送信者の識別のための表示であり「広告又は宣伝」には当たらないと考えられるが、キャッチコピーや訴求文言を添えないこと

### 1-4. 仮に特定電子メールに当たるとしたら何が及ぶか

「該当しない」という整理に依存しきるのは危険なので、該当した場合の義務も確認した。**結論として、表示義務 (法4条1号) だけが現在の運営方針と衝突する。**

| 義務 | 条文 | 本件での充足状況 |
|---|---|---|
| オプトイン (同意なき送信の禁止) | 法3条1項1号 | **充足すると考えられる。** double opt-in による通知先アドレスの登録が「送信をすることに同意する旨を…通知した」に当たる |
| 同意を証する記録の保存 | 法3条2項 / 施行規則4条 | **設計次第。** 下記1-5 |
| 拒否者への送信禁止 (オプトアウト) | 法3条3項 | 充足。RFC 8058 のワンクリック解除 + 設定画面 |
| **表示義務** | **法4条** | **本名・住所の表示が必要になり、現行方針と衝突する。** 下記1-6 |
| 送信者情報を偽った送信の禁止 | 法5条 | 充足。SPF/DKIM/DMARC は Cloudflare が自動構成する。なお法5条は文言上「**特定電子メールの**送信をしてはならない」であり、特定電子メールに当たらない限り同条の適用もない (罰則は法34条1号で1年以下の拘禁刑または100万円以下の罰金) |

**「既定は全部オン」は法的に問題ないと考えられる。** ガイドライン 2①1) p.3 が明示している。

> 同意の範囲について求められているのは、特定電子メールの「送信をすること」であり、**送信する電子メールの種類や内容まで特定して同意をとることまでは、法律上の義務としては求められていない。**

つまり「通知先アドレスを登録する」という1回の作為が同意であり、その中の3種類の内訳が既定オンであることは同意の有効性を損なわない。ただしガイドライン 2①7) p.8 は**デフォルトオフを推奨**しているので、UI 上は3種のチェックボックスを登録画面で見える位置に置き、登録前に外せるようにしておくのが望ましい。

**double opt-in はガイドラインが明示的に推奨している方式である** (ガイドライン 2①5) p.7)。

> 他人の電子メールアドレスを無断で用いて同意の通知をするいわゆる「なりすまし」の同意を防止する必要性が高い場合や、受信者等からの同意の有無に関する問合せに対して同意があることを立証する必要がある場合などには、通知等されたメールアドレスに対し**広告・宣伝内容を含まない確認の電子メールを送付**し、当該電子メールに対して返信等の受信者本人の操作があって初めてその後の特定電子メールについての同意を確定するいわゆる「ダブルオプトイン」を実施することが推奨される。

なお**確認メール自体の扱い**には注意がいる。ガイドライン 2①6) p.7 は「同意の取得・確認のために送信される電子メールは…特定電子メールに該当する」としているが、これは「最終的に広告・宣伝メールを送信するために送信されるもの」であることを理由としている。本件の後続メールが広告・宣伝メールでない以上、確認メールも特定電子メールにならないと考えられる。

### 1-5. オプトイン記録の保存 — 及ぶ範囲と期間

**特定電子メールに当たらないなら、法3条2項の保存義務は及ばない。** ただしガイドラインは、法的義務とは別に記録の保持を推奨している (ガイドライン 2②4) p.13)。

> 法律に基づく義務づけのほか、同意の取得に関して受信者とトラブルが発生した場合など、送信者等の側で同意を適正に取得したことを受信者側に説明する必要がある場合が想定される。この同意の取得に関する説明の必要性は、同意を証する記録の保存の法令上の義務とは別のものであり、送信者等の側では、受信者側とのトラブルの発生の蓋然性に応じ、コスト等も勘案の上、**説明のために最低限必要な記録を保持しておくことが推奨される**。

義務が及ぶ場合の内容と期間は施行規則4条 ([e-Gov / 特定電子メールの送信の適正化等に関する法律施行規則](https://laws.e-gov.go.jp/law/414M60000008066))。

- **保存内容 (1項1号)**: 「通知をした者の個別の電子メールアドレス…に係る**当該通知を受けた時期及び方法その他の当該通知を受けた際の状況を示す記録**」
- **保存期間 (2項2号)**: 「当該送信を**最後にした日から起算して一月**を経過する日までの間」(法7条の措置命令を受けた場合は最長1年に延びる)
- **一度も送らなかった場合 (2項1号)**: 「当該送信をしないこととした日までの間」

**設計への示唆**: 法定の最低ラインは「最後の送信から1か月」と短く、実装上は「登録が有効な間ずっと保持する」ほうがむしろ自然かつ安全である。保持すべきは**登録日時・登録方法 (設定画面のフォーム)・確認メールの検証完了日時**の3点。§A-1 の 2.1 新4号はこれを反映している。

### 1-6. 表示義務 — ここが本件で唯一の実質的リスク

法4条1項は、特定電子メールに「①送信者の氏名又は名称」「②オプトアウトの通知先アドレスまたは URL」「③その他総務省令で定める事項」を「受信をする者が使用する通信端末機器の映像面に正しく表示」させることを求める。③は施行規則9条で「オプトアウトができる旨」「**送信責任者の住所**」「苦情・問合せの受付先」とされている。

**そしてガイドライン 5③ p.27 の注記が決定的である。**

> 注）①の当該送信者の氏名又は名称は、**送信者の正式な氏名又は名称でなければならない。サービスを提供しているウェブサイト名、サービス名（例：○○運営事務局）や屋号、ブランド名称の表示では、送信者名を表示したことにはならない。**

FurDrop は個人事業主による運営で、privacy.md 第8項2号は「代表者の氏名および住所は本ポリシー上では非公表とします」としている。**通知メールが特定電子メールに当たると判定された場合、この方針を維持したままでは法4条を充足できない。**「FurDrop」も「FurDrop 運営事務局」も、ガイドラインが名指しで否定している表示である。

**この一点だけを理由にしても、メール本文から広告・宣伝要素を完全に排除する価値がある**と考えられる。

なお、**付随的に広告が入るケースの緩和規定**もあるが、この問題は解決しない。法3条3項ただし書と施行規則6条は、

> **第六条**　法第三条第三項ただし書の総務省令・内閣府令で定める場合は、次の各号のいずれかに掲げる場合とする。
> 一　契約の申込みをした者又は契約を締結した者に対し**当該契約の申込み、内容又は履行に関する事項を通知するために送信される電子メールにおいて広告又は宣伝が付随的に行われる場合**
> 三　前二号に掲げる場合のほか、**広告又は宣伝以外の行為を主たる目的として送信される電子メール**（電子メールの受信をする者の意思に反することなく送信されるものに限る。）**において広告又は宣伝が付随的に行われる場合**

としており、本件はこの1号・3号に当てはまりそうに見える。しかしこの規定が外すのは**法3条3項 (拒否者への送信禁止) と、法4条1項が明示的に除外する「第二号に掲げる事項」(オプトアウト通知先) と、施行規則9条ただし書による3号事項 (住所・苦情窓口) だけ**である。**法4条1号の「氏名又は名称」は除外されない。** 付随的広告の緩和を使っても、本名の表示義務は残る。

### 1-7. RFC 8058 との関係

[RFC 8058 "Signaling One-Click Functionality for List Email Headers" (2017年1月)](https://www.rfc-editor.org/rfc/rfc8058.html) は `List-Unsubscribe` に HTTPS URI を required とし (§3.1)、`List-Unsubscribe-Post: List-Unsubscribe=One-Click` を伴わせ、両ヘッダを DKIM 署名の対象に含めることを求める (§4)。

**注意点**: これは**ヘッダ**であり、多くのメールクライアントで「配信停止」ボタンとして表示されるものの、法4条2号が要求する「通信端末機器の**映像面に**正しく表示」を確実に満たすとは言い切れない。**本文フッターにも可視の配信停止リンクを置くこと**を推奨する (特定電子メールでないと整理する場合でも、オプトアウト導線としての実務上の意味がある)。

Cloudflare Email Service は RFC 8058 の DKIM 署名要件への準拠を明記している唯一の候補だった ([Email Service / Headers](https://developers.cloudflare.com/email-service/reference/headers/))。

> **List-Unsubscribe**: Must contain `<https://...>` and/or `<mailto:...>` URI(s). HTTP (non-TLS) URIs are rejected. Gmail and Yahoo require this for bulk senders. **Always DKIM-signed per RFC 8058.**
> **List-Unsubscribe-Post**: Must be exactly `List-Unsubscribe=One-Click` (case-sensitive). Requires List-Unsubscribe with an HTTPS URI.

## 論点2: 個人情報保護法 — 何が増えて、どこに効くか

新たに取り扱う個人情報は次の3つ。いずれも**受信者本人から直接取得する**もので、送信者の情報は一切増えない。

1. 通知先メールアドレス (本人の識別に直結する個人情報)
2. 通知の設定 (種類ごとの有効/無効) と検証トークン
3. 通知メールの**本文** — ダイジェストには**送信者名**が入りうる。これは送信者に由来する情報が、これまで通っていなかった経路 (メール配信基盤) を通ることを意味する

### 2-1. 利用目的の特定 (17条) と変更 (17条2項) — 「変更」ではなく「追加」に近い

条文 ([e-Gov / 個人情報の保護に関する法律](https://laws.e-gov.go.jp/law/415AC0000000057)):

> **第十七条**　個人情報取扱事業者は、個人情報を取り扱うに当たっては、その利用の目的（以下「利用目的」という。）を**できる限り特定**しなければならない。
> ２　個人情報取扱事業者は、利用目的を**変更**する場合には、**変更前の利用目的と関連性を有すると合理的に認められる範囲**を超えて行ってはならない。

ガイドライン通則編 3-1-2「利用目的の変更（法第17条第2項、第21条第3項関係）」は、許容範囲をこう述べている。

> 上記3-1-1（利用目的の特定）により特定した利用目的は、変更前の利用目的と関連性を有すると合理的に認められる範囲、すなわち、**変更後の利用目的が変更前の利用目的からみて、社会通念上、本人が通常予期し得る限度と客観的に認められる範囲内**（※1）で変更することは可能である。変更された利用目的は、本人に通知（※2）するか、又は公表（※3）しなければならない。

現行の privacy.md 第3項3号は既に「プッシュ通知（新着写真の通知）の配信」を利用目的として掲げている。メール通知はこの目的の**配信手段の追加**であり、17条2項の「関連性を有すると合理的に認められる範囲」を超えないと考えられる。削除予告・容量警告についても、既存の4号「ストレージ利用状況の表示および管理」および10号「利用規約・本ポリシーの変更通知その他お客様への重要なお知らせの送付」に接続している。

とはいえ**「できる限り特定」(17条1項) の要請があるので、配信手段と通知の種類を明記するほうがよい**。§A-2 の差分案はそのために3号を具体化している。

### 2-2. 通知・公表 (21条) — 設定画面での「明示」が必要になる点に注意

> **第二十一条**　個人情報取扱事業者は、個人情報を取得した場合は、あらかじめその利用目的を公表している場合を除き、速やかに、その利用目的を、本人に通知し、又は公表しなければならない。
> ２　個人情報取扱事業者は、前項の規定にかかわらず、本人との間で契約を締結することに伴って契約書その他の書面（**電磁的記録を含む**。以下この項において同じ。）に記載された当該本人の個人情報を取得する場合その他**本人から直接書面に記載された当該本人の個人情報を取得する場合は、あらかじめ、本人に対し、その利用目的を明示**しなければならない。
> ３　個人情報取扱事業者は、利用目的を変更した場合は、変更された利用目的について、本人に通知し、又は公表しなければならない。

**2つの義務が発生すると考えられる。**

1. **21条3項 (変更した利用目的の通知・公表)** — privacy.md 第13項2項が既に「事前告知 → 効力発生」の手続を持っているので、それに乗せれば足りる。同項は「個情法上の利用目的の変更等、お客様の権利義務に重要な影響を及ぼす変更」に事前告知を求めており、本件はまさにこれに当たる
2. **21条2項 (直接書面取得時の「明示」)** — 設定画面のフォームに通知先メールアドレスを入力させるのは「電磁的記録に記載された当該本人の個人情報を…本人から直接…取得する場合」に当たると考えられる。この場合、**公表 (ポリシーへの掲載) では足りず、取得の時点で「明示」**が要求される。[個人情報保護委員会「個人情報の保護に関する法律についてのガイドライン（通則編）」(令和8年6月一部改正)](https://www.ppc.go.jp/files/pdf/260614_guidelines01.pdf) の 3-3-4「直接書面等による取得（法第21条第2項関係）」(p.48〜50) が、まさにこのケースを名指ししている

   > 個人情報取扱事業者は、契約書や懸賞応募はがき等の書面等による記載、**ユーザー入力画面への打ち込み等の電磁的記録により、直接本人から個人情報を取得する場合には、あらかじめ、本人に対し、その利用目的を明示**（※）しなければならない。
   >
   > 【利用目的の明示に該当する事例】
   > 事例2）ネットワーク上において、利用目的を、本人がアクセスした自社のホームページ上に明示し、又は本人の端末装置上に表示する場合
   > なお、ネットワーク上において個人情報を取得する場合は、**本人が送信ボタン等をクリックする前等にその利用目的（利用目的の内容が示された画面に1回程度の操作でページ遷移するよう設定したリンクやボタンを含む。）が本人の目に留まるようその配置に留意することが望ましい。**
   >
   > （※）「本人に対し、その利用目的を明示」とは、本人に対し、その利用目的を明確に示すことをいい、事業の性質及び個人情報の取扱状況に応じ、内容が本人に認識される合理的かつ適切な方法による必要がある。

   **実装上の要件になる**: 設定画面 (S10) の通知先メールアドレス入力欄の**すぐ近く・登録ボタンを押す前に目に留まる位置**に、「入力されたアドレスは通知の配信にのみ利用します」といった趣旨の1行と、プライバシーポリシーへのリンクを置くこと。ガイドラインが「1回程度の操作でページ遷移するよう設定したリンク」を明示の手段として認めているので、リンク1つで足りると考えられる

### 2-3. 委託 (27条5項1号) と越境移転 (28条) — 行を増やすべきか

> **第二十七条**　…
> ５　次に掲げる場合において、当該個人データの提供を受ける者は、前各項の規定の適用については、第三者に該当しないものとする。
> 一　個人情報取扱事業者が**利用目的の達成に必要な範囲内において個人データの取扱いの全部又は一部を委託**することに伴って当該個人データが提供される場合

Cloudflare Email Service へのメールアドレスと本文の受け渡しは、この「委託」に当たると考えられる。既存の privacy.md 第5項の整理 (Cloudflare = 委託先) がそのまま使える。

**行を増やすべきか、既存行を直すべきか** — **既存行の修正で足りると考えられる。** 理由:

- テーブルの主キーは「委託先」であり、Cloudflare, Inc. は同一法人・同一所在国 (米国)。Google 行が Firebase Auth と FCM の2製品を1行にまとめている既存の粒度とも整合する
- 契約関係が変わらない。Email Service に固有の Service-Specific Terms は**存在しない** (§論点3-2 で確認)
- ただし**「委託する情報の例」に通知メールの本文を明記する**必要はある。本文には送信者名という**第三者 (送信者) に由来する情報**が載るため、「ユーザーアカウント情報」の一語では読み取れない

越境移転 (28条1項) についても、提供先・提供先の所在国・依拠している根拠のいずれも変わらない。

> **第二十八条**　個人情報取扱事業者は、外国…にある第三者（個人データの取扱いについて…**必要なものとして個人情報保護委員会規則で定める基準に適合する体制を整備している者を除く**。…）に個人データを提供する場合には、…あらかじめ外国にある第三者への提供を認める旨の本人の同意を得なければならない。

privacy.md 第6項は「外的環境の把握」の枠組みで書かれており、**情報の種類に依存しない書き方になっている**ので、変更は不要と考えられる。ただし §論点3-1 で述べる「Cloudflare の DPA が日本法をトリガーにしていない」という事実は、そもそもこの「基準適合体制を整備している者」への依拠の強さに関わる。**これは本件で新しく生じた問題ではなく既存の論点だが、あわせて弁護士の確認を受けることを推奨する。**

## 論点3: Cloudflare Email Service の DPA / 利用規約 — 一次情報での確認結果

### 3-1. DPA は Email Service を含むか → 製品名では書かれていないが、"Services" の定義は製品非依存

[Cloudflare Customer DPA](https://www.cloudflare.com/cloudflare-customer-dpa/) §1.1(o):

> "Services" shall refer to all of the cloud-based solutions offered, marketed or sold by Cloudflare or its authorized partners that are designed to increase the performance, security and availability of Internet properties, applications and networks, along with any software, software development kits and application programming interfaces ("APIs") made available in connection with the foregoing.

**DPA 本文には "beta" / "Beta Services" / "Developer Preview" / "Email Service" のいずれの語も現れない。** 製品非依存の包括定義なので Email Service も含まれると読むのが自然だが、**明示の記載はない** — **[一次情報なし]** (Email Service が DPA の対象であることを明言した記述)。

**より重要な発見**: DPA が組み込まれる条件は、DPA 側ではなく [Self-Serve Subscription Agreement](https://www.cloudflare.com/terms/) (Last Updated: September 12, 2025) §6.1 にある。

> If Customer Content includes the personal data of **European data subjects** as those terms are defined by **EU and UK Data Protection Laws** and all data defined as "personal information" under the **California Consumer Privacy Act** ("CCPA") (collectively, "Personal Data"), then Cloudflare is a data processor or sub-processor, as applicable, and Cloudflare will handle such Personal Data in compliance with Cloudflare's Data Processing Addendum ("Data Processing Addendum"), which is hereby incorporated by reference into this Agreement.

**つまり、DPA の発動条件は EU/UK/CCPA の定義する個人データに限定されており、日本の個情法をトリガーにする条項はない。** DPA 全文・Self-Serve Agreement・[Privacy Policy](https://www.cloudflare.com/privacypolicy/) のいずれにも Japan / APPI への言及はない (Zendesk・Oracle のサブプロセッサ所在国としての "Japan" を除く)。

**含意**: privacy.md 第6項4号は「委託先が公表する標準約款・データ処理に関する追補（DPA）等に基づき、適切な保護措置を講じます」と書いているが、**日本の受信者のみを想定するサービス (privacy.md 第1項3号) では、文言上 DPA が自動適用されない可能性がある**。これは Email Service に固有の問題ではなく、既存の R2/D1/Workers/Pages についても同じ構造である。実務的には、①受信者の中に EU/UK/加州の居住者が含まれれば DPA が発動する、②発動しない場合でも Cloudflare の Privacy Policy §6 が「Cloudflare is a data processor for any of the content provided by Customers and End Users through the Services that transits, or in some cases, is stored on, the Cloudflare network」と述べていることを援用しうる、という整理になると考えられる。**専門家の確認を推奨する。**

なお移転メカニズムは EU SCCs (Module Two) + UK Addendum + Swiss の組み合わせ (DPA §6.2)。日本向けの仕組みではない。

### 3-2. Beta の切り出し — DPA は除外されないが、責任は全面的に否定されている

Self-Serve Subscription Agreement §5 "Beta Services" の全文 (要旨を崩さない範囲で抜粋):

> From time to time, we may make non-production Services ("Beta Services") that are under development available to you. … Beta Services are intended for testing purposes only, and may be subject to additional terms that will be presented to you at the time of sign-up or first use. … Cloudflare is not obligated to provide you with support for the Beta Services or correct any bugs, defects, or errors in the Beta Services. … We may discontinue, suspend, or remove Beta Services (including any of Customer Content stored as part of the Beta Services) or your access thereto at any time in our sole discretion and may never make them generally available. … **Notwithstanding Section 12, we will have no liability for any harm or damage arising out of or in connection with any Beta Services.**

**§5 は DPA (§6.1) を除外していない** — 除外しているのはサポート義務と責任 (§12) である。一方で「Customer Content stored as part of the Beta Services」という文言があり、**beta 製品でも顧客コンテンツが保存されうることを Cloudflare 自身が前提にしている**。

**Email Service 専用の Service-Specific Terms は存在しない。** [Application Services](https://www.cloudflare.com/service-specific-terms-application-services/) 等を確認したが、email 関連で見つかるのは Zero Trust の "Cloudflare Email Security (formerly called Area 1)" — これは**受信側のセキュリティゲートウェイであって別製品**である。— **[一次情報なし]** (Email Sending 固有の契約条項)。

**規約への含意**: 「いつでも終了しうる」「損害賠償責任を負わない」ので、通知機能を**サービスの中核機能として約束しない**建て付けが必要。§B-2 の terms.md 第5条新6項 (到達を保証しない) はこれに対応する。

**唯一のメール関連エントリ (AWS) は Email Security = 受信側の別製品**であり、Email Sending 用ではない。Email Sending 固有のサブプロセッサは**載っていない** (自社インフラで完結しているのか、単に一覧が沈黙しているのかはページからは判断できない) — **[一次情報なし]**。

なお **Google LLC が "Cloudflare Developer Platform" のサブプロセッサとして掲載されている**点は、privacy.md 第5項が Google LLC を Firebase の委託先としてのみ掲げていることとの関係で頭の片隅に置いておくとよい (再委託先までポリシーに列挙する義務はないので、記載変更は不要と考えられる)。

### 3-4. Cloudflare 側にメール本文が残るか → 「Email preview」をオンにすると約7日残る

[Email Service / Observability / Logs](https://developers.cloudflare.com/email-service/observability/logs/):

> For sent emails, expand the email in the Activity log to open the **Preview** section and inspect the message as it was sent. The preview provides the following tabs: **HTML**: The rendered HTML body. **Text**: The plain text body. **Headers**: The message headers. **Attachments**: Files included with the message. **Raw**: The full raw RFC 5322 message source.
> To make sent messages previewable, turn on **Email preview** for the sending domain.
> Previews cover messages sent while the setting is turned on and are **retained for about seven days**.

**運用ルールとして提案する**: 本番の送信ドメインでは **Email preview をオフにしておき、障害調査時だけ一時的にオンにする**。ダイジェスト本文には送信者名が載るため、preview をオンにしたままだと「送信者が誰に何枚送ったか」が Cloudflare のダッシュボードに約7日間平文で滞留することになる。オフの状態で Activity log に何がどれだけ残るかは**ドキュメントに記載がない** — **[一次情報なし]** (preview オフ時の既定の保持内容・保持期間)。**GA 時に再確認すること。**

バウンス・苦情の扱いは [Deliverability](https://developers.cloudflare.com/email-service/concepts/deliverability/) と [Suppressions](https://developers.cloudflare.com/email-service/concepts/suppressions/) に記載があり、ハードバウンスしたアドレスは自動的に suppression list に載る。**suppression list の保持期間の記載はない** — **[一次情報なし]**。

## 論点4: 保存期間 — 何を何日と書くか

### 4-1. 規約第13条の「最低3か月」は本件に及ばない

規約第13条は「**送信者の送信行為に関し**、IPアドレス、ユーザーエージェント、タイムスタンプ…を取得し、保存します」と主語を限定し、その目的も「情プラ法第5条所定の発信者情報開示請求その他法令に基づく要請への対応」に限定している。**受信者への通知メールの送達ログは、発信者情報開示の対象になる情報ではない** (開示の対象は「侵害情報の発信者」= 送信者を特定する情報)。

したがって、通知メール関連のログに「最低3か月」の下限を持ち込む必要はなく、**既存の privacy.md 第11項「アクセスログその他の運用上のログ｜原則として90日」に揃えるのが整合的**と考えられる。§A-4 の差分案はこれに従っている。

なお逆方向の整合性も確認しておくと、**通知先メールアドレスの登録・解除の履歴を短く消しすぎると、特定電子メール法3条2項相当の説明責任 (§論点1-5) を果たせなくなる**。「アカウントが有効な間は保持」という設計はこの両方を満たす。

### 4-2. 各データの推奨保存期間

| データ | 推奨 | 根拠 |
|---|---|---|
| 通知先メールアドレス・通知の設定 | アカウント有効中。登録解除またはアカウント削除で削除 | 個情法22条 (不要になったときの消去の努力義務)。既存の「受信者アカウント情報」行と同じ扱い |
| 確認メールの検証トークン | **24時間** | 期限を切ること自体が安全管理措置 (個情法23条)。24時間は double opt-in の実務上の一般的な水準であり、法定の数値ではない — **[一次情報なし]** (トークン TTL に法令上の定めはない) |
| 未検証のまま期限を過ぎた登録 | トークンと同時に削除 (アドレスも残さない) | 検証されていないアドレスは「本人のアドレスである」ことが確認できていない。保持する利用目的がない |
| 通知メールの送達記録 | **90日** | 既存の「アクセスログその他の運用上のログ｜原則として90日」に揃える |
| 登録・検証・配信停止の記録 (登録日時・方法・検証完了日時・解除日時) | アカウント有効中。アカウント削除で削除 | 特定電子メール法3条2項の法定最低ラインは「最後の送信から1か月」(施行規則4条2項2号) だが、ガイドライン 2②4) が説明責任のための保持を推奨している。解除後も**解除したという事実**は残す (再送してしまった場合の説明のため) が、アカウントより長くは持たない |

**アカウント削除 (R15) との関係**: `DELETE /auth/account` の batch に、通知先メールアドレス・通知設定・未使用の検証トークンの削除を含めること。**送達ログについては、規約第13条の保護 (送信者の通信記録) のような残す理由がない**ので、同時に削除してよいと考えられる。architecture.md の削除手順に1行足すことになる。

**Cloudflare 側の残留**: 自前で消しても、Cloudflare の Activity log / preview には残る (§論点3-4)。**preview をオフ運用にすることが、実質的にはこの保存期間表を成立させる前提**になる。

## 論点5: その他の見落としやすい点

### 5-1. 未成年者の同意 — 追記不要と考えられる

privacy.md 第12項と規約第4条は、年齢制限を IDP (X / Google) に依拠する建て付けになっている。メール通知は**既にアカウントを持っている受信者が、自分宛の通知の受け取り方を選ぶ**機能であり、新たに未成年者から同意を取る場面を作らない (通知先アドレスの登録は、規約第2条1項1号で既に成立している利用契約の履行方法の選択にとどまる)。

**唯一の追加リスクは「第三者のアドレスを登録される」ケース**で、これは年齢とは独立の問題。double opt-in がその防止策であり (ガイドライン 2①5) p.7 が「なりすまし」の同意防止として明示的に推奨)、規約側では §B-1 の第3条新6項が「自己が使用する権限を有するメールアドレスのみを登録する」として手当てする。

### 5-2. 退会・アカウント削除時の削除 — architecture.md 側の更新が要る

privacy.md 第11項の「アカウント削除時に削除」という約束は、実装が伴って初めて意味を持つ。architecture.md §4.3 `DELETE /auth/account` の「D1 は batch() で順序保証して以下を実行」のリストに、通知関連テーブルの DELETE を明記すること。**この文書は法務整理なので詳細は書かないが、ドキュメントの更新漏れになりやすい箇所として挙げておく。**

### 5-3. 電気通信事業法27条の12 (外部送信規律) — 追記不要と考えられるが、理由は「サーバ間だから」ではない

条文 ([e-Gov / 電気通信事業法](https://laws.e-gov.go.jp/law/359AC0000000086) 第27条の12):

> …当該利用者の電気通信設備を送信先とする情報送信指令通信（**利用者の電気通信設備が有する情報送信機能（利用者の電気通信設備に記録された当該利用者に関する情報を当該利用者以外の者の電気通信設備に送信する機能をいう。…）を起動する指令を与える電気通信の送信**をいう。…）を行おうとするときは、…あらかじめ、…通知し、又は当該利用者が容易に知り得る状態に置かなければならない。

[総務省 外部送信規律 FAQ](https://www.soumu.go.jp/main_sosiki/joho_tsusin/d_syohi/gaibusoushin_kiritsu_00002.html):

> 問1-2：外部送信とはそもそも何ですか。
> 答：利用者のパソコンやスマートフォン等の**端末に記録された当該利用者に関する情報**を、当該利用者以外の者の電気通信設備（Webサーバ等）に送信することをいいます。

**注意すべき点**: 同 FAQ 問1-16 は「送信先が**当該電気通信役務を提供する事業者自身のサーバであっても規律の対象に含まれる**」と明言している。したがって「自社サーバ宛てだから対象外」「サーバ間通信だから対象外」という粗い理由づけは誤りである。

**規律の可否を分けるのは送信先ではなく起点**、すなわち「**利用者の端末に記録された利用者に関する情報**を、端末側で起動する指令通信によって送信させるか」である。

- **設定画面での通知先アドレスの登録** — 利用者がフォームに打ち込んだ値をサーバへ送るもので、「端末に記録された利用者に関する情報」を第三者へ送信させる指令ではない。対象外と考えられる
- **Workers から Cloudflare Email Service への送信** — 端末が関与しない。そもそも情報送信指令通信ではない。対象外と考えられる
- **通知メールの受信** — 受信者のメールクライアントでの表示であり、当サービスが提供する電気通信役務の画面ではない

**ただし例外的に対象になりうる設計がある**: 通知メールの HTML 本文に**外部ドメインの画像・トラッキングピクセル・外部フォント**を埋め込むと、受信者のメールクライアントが当該外部事業者へ (UA・IP・開封の事実を伴って) リクエストを出す。これが規律の対象になるかは条文上グレー (メールクライアントは「当該電気通信役務」を提供するブラウザ・アプリではない — 施行規則22条の2の27 は「ブラウザその他のソフトウェア…により提供されるもの」に限定している) だが、**プライバシー上の筋としても、本文中の画像は furdrop.app 自身から配信し、開封トラッキングを入れない**のが安全と考えられる。**[一次情報なし]** (HTML メール内の外部リソースが27条の12の対象になるかを直接論じた総務省の見解)。

### 5-4. 開示等請求への影響 — 追記不要だが、実務上の注意が1つ

通知先メールアドレスも保有個人データなので、第8項の開示等請求の対象になる。privacy.md 第8項3号は本人確認の方法として「IDP認証によるログインの確認」を挙げており、これで足りる。

**注意点**: 「通知メールが届いたので、そのメールアドレス宛に開示請求します」という経路を作ってはいけない。**通知先メールアドレスの所持は本人確認の手段にならない** (第三者が登録された可能性、メールボックスの共有等)。privacy.md 第14項が「メールアドレスは、悪用防止の観点から公開していません」としている方針は維持し、**通知メールは no-reply とし、返信・問い合わせはフォームへ誘導する**こと。

### 5-5. 通信の秘密との関係 — 問題にならないと考えられる

当サービスは「不特定の利用者間の通信を媒介する電気通信役務」(規約第5条2項) として運営されており、ダイジェストメールの本文には**送信者名**という通信の内容に由来する情報が載る。

しかしこれは、**通信の当事者である受信者本人に対して、通信の内容を届けている**にすぎない。第三者への漏えいではないので、通信の秘密の侵害にはならないと考えられる。**Cloudflare Email Service を経由する点**についても、既に写真本体が Cloudflare R2/D1/Workers を経由しており (privacy.md 第5項)、電気通信役務の提供に必要な範囲の委託という位置づけは変わらない。**専門家の確認を推奨する。**

**ただしデータ最小化の観点からは、ダイジェスト本文に送信者名を載せない選択肢も検討に値する。** 「新しい写真が3枚届きました」だけでも通知としては成立し、送信者名を見るにはギャラリーを開けばよい。載せなければ、Cloudflare の Activity log / preview (§論点3-4) にも、受信者のメールボックスやメールプロバイダにも、送信者名が流出する経路が1つ減る。**法令上の要求ではなく設計判断**だが、privacy.md 第5項の「委託する情報の例」から「送信者名」を落とせるという副次的な効果もある。

### 5-6. Gmail / Yahoo の一括送信者要件 — 法令ではないが実務上は必須

法的義務ではないが、`List-Unsubscribe` / `List-Unsubscribe-Post` を要求しているのは Gmail・Yahoo の送信者ガイドラインであり、Cloudflare のドキュメントもそれを理由として挙げている ("Gmail and Yahoo require this for bulk senders")。**規約・ポリシーへの記載は不要。**
